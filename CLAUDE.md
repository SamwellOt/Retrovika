# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Retrovika is an all-in-one Android emulation frontend. It is written in Kotlin with Jetpack Compose and has two Gradle modules: `:app` and `:libretrodroid`. The emulation engine is [LibretroDroid](https://github.com/Swordfish90/LibretroDroid), which loads libretro cores (`.so`). It is built from source in `:libretrodroid` (0.13.2 plus fixes for GPU cores, listed in `libretrodroid/README.md`), not taken from JitPack, so it also compiles C++. The NDK is pinned as `ndk` in `libs.versions.toml` (the version preinstalled on the GitHub `ubuntu-latest` runner). CMake is left at AGP's default. If either is missing, AGP installs it into the SDK on the first build. Code comments are in Brazilian Portuguese; keep new ones in Portuguese. The UI is bilingual (English and Portuguese): see **Languages** below.

Keep ROM files and any direct download links out of version control (see `roms/` and `.gitignore`); the catalog metadata is fine to commit.

## Commands

The Android SDK path is in `local.properties` (`sdk.dir`). Export `ANDROID_HOME` to the same path. JDK 17+ is required.

```bash
./gradlew assembleDebug                         # debug APK -> app/build/outputs/apk/debug/
./gradlew assembleRelease                       # R8-minified release (own key via keystore.properties, else debug key)
./gradlew assembleRelease -PbundleCores=all     # embed every core listed in Systems.kt into jniLibs
./gradlew assembleRelease -PbundleCores=snes9x,mgba -PbundleAbis=arm64-v8a,x86_64
./gradlew compileDebugKotlin                    # fast compile check
./gradlew testDebugUnitTest                     # JVM unit tests (app/src/test), no device needed
```

Unit tests cover the pure logic: `DatParser`, `Genre`, `RomNaming`, `Versions`, `CheatFile`, `StatePackage`, `TranslationText`, `CoreBenchmark`, the Backloggd/CDRomance/RomsFun page parsers, `Archives` (including password zips and same-name conflicts), `Http.download` retry and resume (against a local socket server), `GameTitles`, `GameFiles.referencedPaths`, `BiosManager.unsatisfied`, `FileNames`, the consistency of the `Systems` catalog, and the remote-play server (`RemoteServer` over a real socket, WebSocket framing, `Fmp4`/`VideoTrack`, `LanAddress`). `RegexSyntaxTest` reads the sources and rejects regexes with an unescaped `{` or `}`: the JVM accepts them, but Android's ICU throws `PatternSyntaxException`, and in a `companion` that kills the app at startup (0.5.0 shipped like that). `unitTests.isReturnDefaultValues` is on, so code that touches `android.*` returns defaults instead of throwing. There are no instrumented tests and no lint config. The `startup-smoke` workflow builds the R8 release APK, opens it on API 29 and 34 emulators and fails if the app dies within 20 s (logcat in the job artifacts); run it by hand with a `release` tag to test a published APK. Verify UI and emulation changes on a device:

```bash
adb install -r app/build/outputs/apk/debug/app-debug.apk
adb shell am start -n com.retrovika.app/.MainActivity
adb shell am start -n com.retrovika.app/.emulation.GameActivity --el game_id <id>   # works from a root adb shell
adb exec-out screencap -p > shot.png
```

App data lives in `/sdcard/Android/data/com.retrovika.app/files/Retrovika/`, with subfolders `roms/<systemId>/`, `saves/`, `states/` and `system/`. Cores live in internal `filesDir/cores/`. The DB is `/data/data/com.retrovika.app/databases/retrovika.db`.

## Architecture

**Dependency wiring.** `RetrovikaApp` builds one `AppContainer` holding the repositories and managers. It uses no DI framework. Composables reach it with `LocalContext.current.container` (an extension on `Context`). ViewModels are created with `viewModel { XViewModel(context.container) }`.

**Systems catalog.** `core/systems/Systems.kt` is the single source of truth for consoles. Each `GameSystem` declares:
- file extensions
- an ordered core list (the first entry is the default)
- per-core option `defaults` and `presets`
- BIOS files with MD5 hashes
- orientation
- a `PadLayout` from `emulation/input/PadLayout.kt`
- `libretroDbName`, used for thumbnail URLs

- `keepArchives` for systems whose core runs the `.zip` itself (arcade, DOS), so downloads are not extracted
- `folderOnlyExtensions` for extensions too generic to identify the console on their own (PICO-8 `.png`)
- Citra only presses the 3DS touchscreen with `citra_touch_touchscreen=enabled` (off in the core); its default "mouse" mode moves the cursor with the pointer but presses only with a mouse button, which LibretroDroid never sends. `Systems.kt` sets both
- `portDevice` for cores that ignore input until the frontend calls `retro_set_controller_port_device` (Flycast, Dolphin, Opera, PC-FX, PUAE, VICE, Caprice32, fMSX). It is set on every port before the first `retro_run`. Don't add it to every core: on atari800 a plain JOYPAD replaces its 5200 controller
- BIOS entries without a single MD5 can declare a `format` (`BiosFormat.PS2`): `BiosFormats` checks the content with the core's own rules, Ajustes shows `INVALID` for a right name with wrong content, and import accepts a valid file under any name
- BIOS entries can share a `group`: the group is satisfied when any one file in it is present (3DO, Neo Geo CD)

To add a console, you mostly just add an entry here, plus folder aliases in `RomNaming` and, for cartridge systems with a No-Intro DAT, an entry in `DatCatalog`. `SystemsTest` checks the catalog for consistency. The Gradle `fetchCores` task finds core IDs by regex-matching `CoreInfo("<id>"` in this file, so keep that literal form.

**Cores.** `CoreManager.corePath()` first looks for a core bundled in the APK (`nativeLibraryDir/lib<id>_libretro_android.so`). If there isn't one, it uses the downloaded `filesDir/cores/<id>_libretro_android.so`. Missing cores are downloaded from `buildbot.libretro.com/nightly/android/latest/<abi>/` and marked read-only, which Android 14+ requires for dlopen. They must stay on internal storage. Some cores need `systemAssets` from `buildbot.libretro.com/assets/system/` (PPSSPP, Dolphin's `dolphin-emu/Sys`, LRPS2's `pcsx2/resources`, blueMSX's `Machines`/`Databases`). They are extracted into `system/`, and a `.asset-<name>` marker is written only after extraction completes. `CoreManager.needsInstall()` checks both the `.so` and the markers, and installs are serialized per core.

**Core options at launch.** Options are merged in this order: `core.defaults`, then `core.presets[preset]`, then the user's manual overrides stored in DataStore under `core_options_<coreId>`. A value the core does not list for that key is replaced by the core's default when the core declares its options, so keys and values in `Systems.kt` must match the core's own list (check with the core's `SET_VARIABLES`). Before creating the view, `GameActivity` points `$EXTERNAL_STORAGE` at `saves/<system>/`, because Play! builds its data folder from it.

**Library.** `LibraryRepository.rescan()` merges two sources:
- the internal `roms/<systemId>/` tree (plain file paths, `GameSource.IMPORTED`/`DOWNLOADED`)
- user folders linked through SAF (`content://` URIs, `GameSource.LOCAL`), scanned directly with `DocumentsContract` for speed

`RomNaming` decides the system: a folder alias (`ps1`, `megadrive`, …) wins over the file extension, and an extension only identifies a system on its own if it is unique (`Systems.byUniqueExtension`). Scans read every `.cue`/`.gdi`/`.m3u`/`.ccd` first, and only the files those sheets reference are hidden as auxiliary. When a sheet can't be read, `isAuxiliaryFile` falls back to a name heuristic. Removing a SAF game adds its URI to `hiddenGames` in settings, so the rescan doesn't bring it back; Ajustes can unhide them.

**Launching games.** Path-based games pass `gameFilePath` to LibretroDroid. A SAF game on local storage also gets a real path when the user granted all-files access (`StorageAccess.realFile`). Cores marked `needsRealPath` (Play!, bsnes, Mesen, ParaLLEl N64, Panda3DS, SameDuck) open the game with their own I/O instead of the libretro VFS; without that permission they show a screen asking for it, because the virtual path does not exist for them. Otherwise SAF games go through `GameFiles.virtualFiles()`, which opens file descriptors for the main file plus any `.cue`/`.gdi`/`.m3u` references under the fake directory `/retrovika_vfs/`. LibretroDroid's VFS matches those paths by exact string, so references keep their relative subfolder (`disc1/x.cue`) as written in the sheet.

**GameActivity lifecycle (important).** LibretroDroid is a native singleton, which has several consequences:
- `GameActivity` is `singleTask` with its own `taskAffinity`. `onNewIntent` with a different game ID saves and then calls `recreate()`.
- `GLRetroView` observes a private `LifecycleRegistry` (`emulationOwner`), not the Activity's lifecycle. Pausing means moving that registry to `STARTED`. This is how the pause menu freezes emulation.
- In `onPause`, SRAM and the autosave state are written synchronously *before* the registry is moved down.
- Never serialize, unserialize or reset the core off the emulation (GL) thread. GPU cores (N64, Dreamcast, GameCube) make GL calls there and crash or write garbage without the context. The GL thread is stopped while paused, so the state is captured before stopping (on menu open and in `onPause`) into `frozenState`. The menu saves and autosaves from that copy. Load and reset close the menu first, then run on the emulation thread, waiting from `Dispatchers.Default` rather than the main thread. SRAM is a plain memory copy and can be read from any thread.
- The manifest `configChanges` stops rotation from recreating the Activity.
- `GameScreen` keeps the `AndroidView` at the same composition position in both orientations, so the GL surface is never re-parented.

**Saves.** SRAM is stored as `saves/<system>/<rawName>.srm`, the same naming RetroArch uses. States are `states/<system>/<gameId>/slot<N>.state` plus `.png` thumbnails. Slot 0 is the autosave, and its thumbnails come from `PixelCopy`.

**Virtual gamepad.** `VirtualGamepad` gives every control its own `pointerInput`. This is what makes multi-touch work, and it lets touches outside the controls reach the game view (needed for the DS touchscreen). `PadMetrics` holds nominal dp sizes and computes an auto-scale that fits the portrait or landscape area. If you add a `FaceArrangement` or change control sizes, update `PadMetrics` too. Key codes follow the libretro RetroPad convention (A = right, B = bottom, X = top, Y = left). The D-pad and the N64 C-buttons send motion events, not key events.

**Catalog and downloads.** `CatalogSource` implementations are registered in `CatalogRepository`: `CdRomanceSource`, `RomsFunSource` (only when built with a `WebFetcher`, so JVM tests create the repository without it), `HomebrewHubSource` and `InternetArchiveSource`. The list order is also the preference order: `CatalogRepository.mergeDuplicates` joins every page of the same game (same system and normalized title, `dedupKey`; a trailing "DVD5"/"DVD9" is ignored) into one card, whether the pages come from different sources or repeat inside one (RomsFun has several pages for some games). The card keeps the position where the game first appeared, the entry of the earliest source in the list is the main one and the rest go to `CatalogEntry.alternates`. `ExploreViewModel` applies it again as each page or source arrives, and in single-source views too. `downloadKey` is the `dedupKey`, so it doesn't change when a card is merged. In the Explore source filter, CDRomance and RomsFun are one chip, "Roms" (`ROMS_GROUP` in `ExploreViewModel`, `searchAll(only = …)`), and cards tag them as "Roms" too; the real site name only shows when downloading (variant picker, game page's download panel). On the game page, `CatalogRepository.variants` lists the files of every merged page in parallel, each `RomVariant.origin` pointing at its page (a failing source doesn't hide the others), `directLink` uses that origin, and `details` falls back to the next page when the main one fails. In `HomebrewHubSource`, search uses `q`, because `title` is case-sensitive, and `developer` can be a string or an array. A source can override `directLink(entry, variant)`: it runs inside the download job (and again on retry), for links that are signed and expire. The Explore tab has special **genre filters** (`core/catalog/Genre.kt`): no source has a real genre taxonomy, so `search(..., genre)` is best effort per source. Homebrew Hub sends the genre to its API as a `tags=` filter (`hubTag`: server-side, so pages are not empty; filtering locally made sparse genres chain request after request), CDRomance appends `Genre.searchTerm` to the WordPress `?s=` search, run inside the console's section (`/<section>/?s=`) when a console is chosen so the site filters it, the Internet Archive adds a `subject:(…)` clause, and RomsFun uses the site's own genre taxonomy (`GENRE_TERMS`). The UI says results are approximate. `CatalogRepository.search` caches recent pages for a few minutes, and `searchAll(onPartial = …)` shows each source as soon as it answers. When a filter yields few games per page, `ExploreViewModel` fetches the next pages in parallel (`PARALLEL_PAGES`) until the screen is filled. `DownloadManager` runs downloads in the app scope through a queue: at most `AppSettings.maxDownloads` run at once (the rest stay `QUEUED` and start in the order they were requested), and each task keeps its work so `retry(id)` can redo it. Tasks report bytes, total and a smoothed speed from `Http.download(onBytes = …)`; UI that only needs the counter observes `activeCount`, not `tasks`, so it doesn't recompose on every progress tick. It extracts `.zip`/`.7z` through `RomExtractor` (except for arcade; disc games with `.cue`/`.gdi`/`.m3u` get every track extracted), and registers the result through `LibraryRepository.addDownloaded`. `LibraryRepository.importFiles` uses the same extractor. `Archives` detects the format by magic bytes and uses commons-compress `ZipFile`/`SevenZFile`, so Deflate64/ZIP64 work. `.7z` goes first through `SevenZipNative` (`app/src/main/cpp`, the public-domain LZMA SDK in `cpp/lzma/`), which decodes Copy/LZMA/LZMA2 blocks in chunks with the dictionary in native memory: "ultra" archives need 256 MB+ of dictionary, more than the Java heap of many phones even with `largeHeap`. Other methods (BCJ, BCJ2, PPMd) fall back to commons-compress before anything is written. Password-protected archives (encrypted `.zip` via zip4j, AES `.7z` via commons-compress, which skips the native path) are opened with the passwords that sites publish (`RomExtractor.KNOWN_PASSWORDS`). `Http.download` waits and retries on 503/429 (ROM file hosts answer "server is busy" under load), honoring `Retry-After` (capped at 5 min) for up to 16 minutes in total, and reports each wait through `onWait`; `DownloadTask.retryAt` shows it as a countdown (`busyWaitText`). It also resumes with Range when a connection drops. Every failure must reach the screen as a readable reason: throw `LocalizedException`, and show it with `Throwable.userMessage(context)`, which also turns network and disk errors into plain text.

**RomsFun.** Everything on romsfun.com is behind a Cloudflare challenge (OkHttp gets 403), so `RomsFunSource` has its own `WebFetcher` (`minGapMs = 400`: about 30 quick fetches give 429 plus a new challenge; `WebFetcher.request` then reopens the site and retries once). Search is `/browse-all-roms/` with `q`, `consoles[]` (numeric ids, all supported consoles when none is chosen, so pages aren't full of PS3/Xbox games) and `genres[]`; the site's `/?s=` ignores genre. Download: the game page links `/download/<slug>-<id>`, whose table lists the files. For 3DS, `.cia`, "eShop" and "(Theme)" rows are dropped because the core can't run CIA; a table with only those raises `romsfun_only_cia`. Each file page `/download/<slug>-<id>/<n>` gets its real link from `POST admin-ajax.php` `action=k_get_download`, with the file page as `referrer`. The `href` already in the page HTML is a decoy that the server rejects. The signed link (`sto*.romsforever.co`, `sto.romsfast.com`) only works from the IP that requested it: `directLink` reads the WebView's IP from `/cdn-cgi/trace` and pins OkHttp to IPv4 or IPv6 (`Http.clientFor`); a mismatch returns 403 "Sorry, your request is invalid". When a file host shows its own challenge, `WebFetcher.solve()` opens it in the WebView, and OkHttp sends that `cf_clearance` with `WebFetcher.userAgent`. The fetcher must not block images: the challenge never finishes without them. File hosts: `sto.romsfast.com` (no challenge, but IP-pinned), `sto2.romsforever.co` (challenge; a Google Drive index that answers big files with 503 `{"error":"The server is busy…"}` and `Retry-After: 300` even when the 1-byte probe passes) and `statics.romsfun.com` (challenge for OkHttp from desktop, passes from Android). Too many requests from one IP make the file hosts answer 503 for minutes (up to an hour), so test sparingly. Some `og:image` URLs are `http://` and are upgraded to https.

**Catalog game page.** Tapping an Explore card opens `catalog/{key}` (`ui/screens/explore/CatalogGameScreen.kt`); the route carries only the `downloadKey`, and `CatalogRepository.open/opened` keeps the entry in memory while the page exists. `CatalogGameViewModel` loads its parts in parallel, each as a `Part` (loading, ready, failed), so a failure never hides the rest:
- `CatalogSource.details(entry)`: the source's own sheet (`SourceDetails`). RomsFun reads the header (rating, downloads, genre), the info table, `.page-content` and `#romGallery`. CDRomance reads the `table.rom-info` rows, the users' `aggregateRating`, `#custom-description` and the `#lightgallery` screenshots (the game page is cached, since the download reads it again). Homebrew Hub reads `/api/entry/<slug>.json`; the Internet Archive reads `/metadata/<id>`.
- `variants(entry)`: the files; sizes the listing lacks come from a `HEAD` (`Http.contentLength`).
- Backloggd (`core/gameinfo/BackloggdClient`): no public API, so it uses the site's `autocomplete.json` and parses the game page (JSON-LD `AggregateRating`, `#ratings-bars-height` histogram) plus `/reviews/preview/<slug>/`. Among same-name games it keeps the earliest one released on the console (`Platforms` maps system IDs to IGDB platform slugs/names). Its BunnyCDN sometimes answers with a JavaScript check (403, "Establishing a secure connection"), depending on the IP; the cookie it sets only works on the browser's own connection, so from then on `WebFetcher` makes the requests from inside an invisible WebView with `fetch()` (results come back through a `@JavascriptInterface`).
- Wikidata/Wikipedia (`WikiClient`): found by the Backloggd slug (it is the IGDB slug, Wikidata `P5794`) or by title; gives developers, publishers, series, director, composer, modes, age ratings, critic scores (`P444`/`P447`), links (HowLongToBeat, MobyGames, Metacritic, IGDB) and the article summary in the app language.
- HowLongToBeat (`HowLongToBeatClient`): the time to beat comes from here, not from Backloggd. The game ID is Wikidata's `P2816` (`WikiInfo.hltbId`), so it loads after Wikipedia; `/game/<id>` works with plain OkHttp (browser User-Agent) and carries everything in `__NEXT_DATA__`: main story, main + extras, completionist, all styles and speedrun (`comp_*` in seconds, `comp_*_count` players). The site's search needs a rotating token, so games without the Wikidata ID just don't show the section.
`GameInfoRepository` caches Backloggd, Wikipedia and HowLongToBeat for 15 minutes. `GameTitles.clean` turns ROM names into database titles. `GameInfoNetworkTest` checks all of this against the real sites in the `catalog-speed` workflow.

**In-app browser.** `ui/screens/browser/BrowserScreen.kt` is a WebView for sites that can't be a `CatalogSource` (Cloudflare challenges, token flows). The user browses normally; `DownloadListener` captures the file, `RomNaming.guessSystem` pre-selects the console from the extension or page URL/title, and `DownloadManager.enqueueBrowser` downloads it with the WebView's cookies, User-Agent and Referer. `Http` keeps a User-Agent set on the request instead of overriding it.

**Visual identity.** The theme is "synthwave sunset" (`ui/theme/Theme.kt`). `Palette.Neon` (pink) is the primary accent, `Cyan` the secondary, and `SunsetGradient`/`SunsetHorizontal` (pink → orange → yellow) are used for primary buttons, the active tab and the brand. Fonts are bundled in `res/font` (OFL): Space Grotesk (`DisplayFamily`, the Material typography), JetBrains Mono (`MonoFamily`, labels) and Press Start 2P (`PixelFamily`, only for `Wordmark` and `Kicker`). Build screens from the shared pieces in `ui/components/Components.kt`: `ScreenHeader`, `HeaderIconButton` (every round header button, with optional badge/busy state), `SectionHeader`, `GradientButton`/`GhostButton`, `SelectChip`/`AccentChip`/`ChipStrip` (instead of M3 `FilterChip`; chips are `selectable`, min 36dp tall), `FilterLabel`, `Modifier.bleed()` (chip strips inside a padded grid run to the screen edge), `Modifier.shimmer()`/`GameCardSkeleton` (loading placeholders instead of a lone spinner), `IconTile`, `SearchField`, `SurfaceCard`, `DownloadProgressBar`, `EmptyState(icon = …)` and `Modifier.ambientGlow()`. The tab bar floats over the content, so tab screens add `LocalBottomInset.current` to their bottom `contentPadding`. The logo is an "R" whose counter is a play button, in front of a striped sun: `ic_launcher_background` (scene) + `ic_launcher_foreground` (monogram) + `ic_launcher_monochrome`; `ic_logo` (layer-list) is used by the splash, and `BrandMark` draws it in Compose.

**Languages.** No user-visible string is hardcoded in Kotlin. Strings live in resources: `res/values/` is English (the fallback for any other system language) and `res/values-pt/` is Portuguese. Every key must exist in both. `strings.xml` holds the shared keys (`common_*`, `tab_*`, the `games_count`/`consoles_count` plurals, `region_*`), and each area has its own `strings_<area>.xml`. Enums and catalog data carry `@StringRes` ids, not text (`Preset.label`, `ShaderOption.label`, `CoreInfo.description`, `BiosFile.description`). Use `stringResource`/`pluralStringResource` in composables. Outside the UI, use `context.localized().getString(...)`, because the Application context isn't recreated when the language changes below Android 13. Regions are stored in the DB in Portuguese at scan time (`RomNaming.region`, `regionOf`) and translated only at display time with `regionLabel()`. The language picker in Ajustes goes through `core/settings/Languages.kt`:
- On Android 13+ it uses the system per-app language (`LocaleManager`, `res/xml/locales_config.xml`).
- Below that, it stores the choice in SharedPreferences and `Languages.wrap` is applied in `attachBaseContext` of the Application, `MainActivity` and `GameActivity`.

**Navigation.** `ui/navigation/RetrovikaNavHost.kt` uses string routes. The tabs are `home`, `library`, `explore`, `downloads` and `settings`; pushed screens are `system/{id}`, `game/{id}`, `catalog/{key}`, `browser`, `settings/cores` and `settings/bios`. Tapping the open tab again emits its route on `LocalTabReselect`, and each tab screen calls `ScrollToTopOnReselect(route, state)` with its list state. `AppSettings.reduceMotion` turns the screen transitions off. The NavHost also owns the SAF folder-picker launcher and runs a rescan on startup.

**Repeated versions.** `core/library/Versions` groups a console's files by clean title (the DAT name when identified; disc numbers stay in the key, so disc 2 is never a "duplicate" of disc 1) and scores each one: the app language's region or a translation into it (`[T+Por]` beats the English original for Portuguese users), DAT verification, `[!]` and newer revisions win; `[b]`, hacks, trainers and betas lose. `system/{id}/versions` shows the groups, bulk-verifies with `DatRepository.identifyAll` and removes the others.

**Cheats.** `CheatRepository` lists `libretro-database/cht/<libretroDbName>/` through the GitHub API (`contents/cht` for the folder SHA, then `git/trees/<sha>`, because the contents API stops at 1000 files) and caches the list for a week. Per-game choices live in `cheats/<system>/<id>.json`. `CheatSession` backs the pause-menu tab; the activity re-applies the whole enabled list (`resetCheat` + `setCheat`) on the emulation thread when the menu closes and after the first frame.

**Controller per game.** Besides `pad_console_<system>`, a game can have its own `pad_game_<id>` profile (menu › Controls › "This game only"). Profile writes go through an ordered, unbounded queue because each one may target a different key.

**Sharing states.** A `.rvstate` is a zip (`manifest.json`, `state.bin`, `thumb.png`, see `StatePackage`). It goes out through the share sheet (FileProvider `${applicationId}.files`) or over the LAN: `LanTransfer.Server` serves it on a raw TCP socket with a token (no HTTP: cleartext is blocked and there is no certificate for a LAN IP) while a `retrovika://state` QR code is on screen. `MainActivity` turns VIEW/SEND intents and deep links into `AppContainer.incoming`; `ReceiveHost` matches the game (`StatePackage.match`: DAT name, raw name, file name, then title with the same region) and launches `GameActivity` with `state_file`/`core_id`. Such a session (and a netplay guest) is a `guestSession`: neither SRAM nor autosave is written.

**Live translation.** `LiveTranslator` runs ML Kit's Japanese text recognizer (unbundled, model installed through Google Play services via the `ocr_ja` manifest dependency; it also reads Latin text) and ML Kit on-device translation, falling back to `translate.googleapis.com` when the model can't be downloaded. Japanese is always translated; English only for Portuguese users. The activity captures the frame and the state (like opening the menu), pauses, and `TranslationOverlay` draws each translation over its original box.

**Core benchmark.** The first time a console runs without a user-chosen core (`AppSettings.autoBenchmark`), `GameActivity.runBenchmark` runs every stable core with the game for a few seconds, muted, at `frameSpeed` 8, each with its own `LifecycleRegistry`. Speed = emulated frames (`LibretroDroid.getRunCount`) / time / content fps. `CoreBenchmark.choose` keeps the first core in catalog order with ≥130% speed, else the fastest. Results live in `bench_<system>`; `effectiveCoreFor` = user choice ?: benchmark. Progress is written to `filesDir/benchmark_<system>.json` before each core, so a core that crashes the app counts as failed on the next launch.

**Local netplay.** `libretrodroid/.../netplay.cpp` is input-delay lockstep: before each `retro_run` of frame F each side sends its input for F + delay and runs F only once the other side's input for F arrived; otherwise the frame is skipped (the GL thread never blocks on the network). `handleSetInputState` answers ports 0/1 from the synchronized pads while a match is on. The Kotlin side (`core/netplay`, `NetplayController`) pairs through a `retrovika://netplay` QR code and uses two TCP sockets: control (text lines `INFO`/`JOIN`/`OK`/`STATE`/`RESYNC`/`BYE`) and input, whose fd is detached and handed to native. The host serializes the state and starts netplay in one emulation-thread step (`serializeAndStartNetplay`); the guest does the mirror (`unserializeAndStartNetplay`). Fast-forward, state loading, reset, core options and cheats are blocked during a match.

**App updates.** `core/update/AppUpdater` reads `api.github.com/repos/SamwellOt/Retrovika/releases/latest` once per process (`checkOnStartup`, off with `AppSettings.checkUpdates`) or from Ajustes › Atualizações, compares the tag with `versionName` (`Versions.newer`), downloads the attached `.apk` into `cacheDir/updates/` and checks that its package and signing certificate match the installed app before handing it to `PackageInstaller`; `UpdateInstallReceiver` opens the system confirmation (`STATUS_PENDING_USER_ACTION`) and reports failures. `UpdateCard` shows it on Home ("Depois" stores `dismissedUpdate`) and in Ajustes. The release notes come from `.github/release-notes/<tag>.md`, so keep them readable as plain text.

**Remote play** (`remote/`, pause menu tab "Tela e controles"). `RemotePlay` (in `AppContainer`) runs `RemoteServer`, a hand-written HTTP + WebSocket server (no dependency; one thread per connection plus a writer thread and queue each, so a slow device never blocks the encoder), on port 8080 or a free one, bound only to the Wi-Fi/hotspot address from `LanAddress` (never all interfaces: the mobile-data side can have a public IPv6; `LanAddress` also skips `rmnet`/`ccmni`/VPN interfaces, whose 10.x CGNAT addresses look private). The server pings every connection every 10 s and drops one silent for 35 s, and a device reconnecting with the same `id` replaces its old connection (the old tab gets `replaced` and stops reconnecting), so a phone that left the Wi-Fi doesn't keep its player slot. Any exception in a connection thread is caught, since an uncaught one would kill the app. While the server runs it holds a Wi-Fi lock (`WIFI_MODE_FULL_LOW_LATENCY`, `HIGH_PERF` below Android 10): in power-save mode the phone's Wi-Fi only receives on the router's beacons, about 100 ms apart. Two pages from `assets/remote/`, bilingual by `navigator.language`, need no app:
- `pad.html` (the QR code opens `/pad?c=<code>`): a touch controller built from the console's `PadLayout` (`RemotePlay.layoutJson`), one WebSocket per phone. Each gets the lowest free port 1–3 (port 0 is the game phone, ports of physical controllers are skipped) and gets the same one back when it reconnects (`id` in localStorage). Messages are JSON `k` (key) and `m` (motion, the same sources as `PadListener`); on disconnect everything it held is released. Core rumble for that port goes to the phone (`navigator.vibrate`).
- `tv.html` (`http://<ip>:8080`, 6-digit code): the game with sound. It can also ask for players (`join` with a local `p` slot) for the keyboard and Gamepad API controllers on that computer.

Video: after each rendered frame, `Capture` (`libretrodroid/src/main/cpp/capture.cpp`) copies the game area of the window into a texture (`Video::copyForeground`) and, with the `VideoEncoder` input surface current, draws it there (`drawCapture`) on the emulation thread. Don't blit straight from the window with the encoder as draw surface: ANGLE scales that cross-surface read by the wrong surface size. GLES 3 only (`GLRetroView.supportsCapture`). H.264 (Baseline, 1280x720, 6 Mbps) goes out as fragmented MP4 (`Fmp4`) played through Media Source Extensions, which also works on plain `http://`, unlike WebCodecs and AudioWorklet. `VideoTrack` holds each frame until the next arrives and gives it the exact duration: MSE treats a jump bigger than twice the previous duration as a discontinuity and drops everything until the next keyframe. The page keeps near the newest frame, checked after every append (seek when > 0.25 s behind, 1.25x when > 100 ms, 1.1x when > 50 ms). Binary packets start with a type byte: 1 init, 2 video, 4 video keyframe, 3 audio. When the page has to drop queued frames it restarts at a keyframe (or asks for one with `key`), and on a player error it sends `restart` to get the init segment again. `VideoEncoder` has four modes, from lowest latency to most compatible (hardware realtime + low latency, low latency only, plain, software): when the codec dies after starting (Xiaomi SM6375 with `KEY_PRIORITY` realtime), fails to start, or no frame arrives within 12 s, `RemotePlay` stops the capture and tries the next one; the mode that delivered video is saved per app version (`remote_play` prefs). Only after the last mode fails do the menu and the page say so. Audio: `handleAudioCallback` also copies samples into a ring buffer (`Capture::writeAudio`, before the "audio enabled" check, so the phone can be muted while the TV plays); `RemotePlay` sends 20 ms PCM chunks that the page schedules with Web Audio. The encoder runs only while a screen is connected. The server survives game changes (`recreate()` re-attaches the new `GLRetroView`) and stops when the game is exited (`isFinishing`). Wrong codes are counted per IP (20 in a minute gives 429) and across all IPs (60), on the WebSocket and on `/qr.svg` alike. Test it with headless Chrome over CDP against the redroid address; its display runs at 15 Hz, so it only emulates about 30 frames a second, with or without streaming.

**Diagnostics.** Ajustes › "Enviar relatório de erros" (`core/diagnostics/ErrorReport`) shares device/GLES info, `ApplicationExitInfo` and the app's own recent logcat, which still holds the native backtrace and core messages of a crashed game on the next launch. Ask users for it when a core crashes on a device you can't reach.

## Constraints

- Library versions are pinned in `gradle/libs.versions.toml` (AGP 8.13, Kotlin 2.2, compileSdk 36). AGP 9.x is not in use.
- Release signing reads `keystore.properties` (template: `keystore.properties.example`) or `RETROVIKA_*` env vars, and falls back to the debug key with a warning locally. The `release.yml` workflow fails without the `RETROVIKA_KEYSTORE_BASE64` secret: every release must be signed with the same project key (from 0.3.4 on), or the in-app updater can't install it over the previous one. Never commit the keystore or its properties.
- With targetSdk 36, Android 16 delivers Back only through `OnBackPressedDispatcher`, not as `KEYCODE_BACK`. `GameActivity` handles both paths.
