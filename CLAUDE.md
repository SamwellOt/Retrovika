# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Retrovika is an all-in-one Android emulation frontend. It is written in Kotlin with Jetpack Compose and has two Gradle modules: `:app` and `:libretrodroid`. The emulation engine is [LibretroDroid](https://github.com/Swordfish90/LibretroDroid), which loads libretro cores (`.so`). It is built from source in `:libretrodroid` (0.13.2 plus fixes for GPU cores, listed in `libretrodroid/README.md`), not taken from JitPack, so it also compiles C++. The NDK is pinned as `ndk` in `libs.versions.toml` (the version preinstalled on the GitHub `ubuntu-latest` runner). CMake is left at AGP's default. If either is missing, AGP installs it into the SDK on the first build. Code comments are in Brazilian Portuguese; keep new ones in Portuguese. The UI is bilingual (English and Portuguese): see **Languages** below.

Keep ROM files and any direct download links out of version control (see `roms/` and `.gitignore`); the catalog metadata is fine to commit.

## Commands

The Android SDK path is in `local.properties` (`sdk.dir`). Export `ANDROID_HOME` to the same path. JDK 17+ is required.

```bash
./gradlew assembleDebug                         # debug APK -> app/build/outputs/apk/debug/
./gradlew assembleRelease                       # R8-minified release (own key via keystore.properties, else debug key)
./gradlew assembleRelease -PbundleCores=all     # embed every core listed in Systems.kt into jniLibs
./gradlew assembleRelease -PbundleCores=snes9x,mgba -PbundleAbis=arm64-v8a,x86_64
./gradlew assembleRelease -PabiSplits             # also one APK per ABI next to app-universal-release.apk (release.yml uses it)
./gradlew compileDebugKotlin                    # fast compile check
./gradlew testDebugUnitTest                     # JVM unit tests (app/src/test), no device needed
```

Unit tests cover the pure logic: `DeviceProfile` tiers, `Tuning` (precedence, the level search, `withoutAutoFrameskip`) and `SpeedWatch` (including the frameskip signal), `Thermal`, `VulkanHealth` and `SessionGuard`, `DatParser`, `Genre`, `RomNaming`, `Versions`, `CheatFile`, `StatePackage`, `TranslationText`, `MeikiDecode`, `GeminiText`, `RemoteZip`, `CoreBenchmark`, the Backloggd/CDRomance/RomsFun page parsers, `Archives` (including password zips and same-name conflicts), `RZip`, `SaveStates` (async writes awaited by reads), `Http.download` retry and resume (against a local socket server), `GameTitles`, `GameFiles.referencedPaths`, `BiosManager.unsatisfied`, `FileNames`, the consistency of the `Systems` catalog, and the remote-play server (`RemoteServer` over a real socket, WebSocket framing, `Fmp4`/`VideoTrack`, `LanAddress`). `RegexSyntaxTest` reads the sources and rejects regexes with an unescaped `{` or `}`: the JVM accepts them, but Android's ICU throws `PatternSyntaxException`, and in a `companion` that kills the app at startup (0.5.0 shipped like that). `unitTests.isReturnDefaultValues` is on, so code that touches `android.*` returns defaults instead of throwing. There are no instrumented tests and no lint config. The `startup-smoke` workflow builds the R8 release APK, opens it on API 29 and 34 emulators and fails if the app dies within 20 s (logcat in the job artifacts); run it by hand with a `release` tag to test a published APK. Verify UI and emulation changes on a device:

```bash
adb install -r app/build/outputs/apk/debug/app-debug.apk
adb shell am start -n com.retrovika.app/.MainActivity
adb shell am start -n com.retrovika.app/.emulation.GameActivity --el game_id <id>   # works from a root adb shell
adb exec-out screencap -p > shot.png
```

App data lives in `/sdcard/Android/data/com.retrovika.app/files/Retrovika/`, with subfolders `roms/<systemId>/`, `saves/`, `states/`, `cheats/`, `translations/` and `system/`. Cores live in internal `filesDir/cores/`. The DB is `/data/data/com.retrovika.app/databases/retrovika.db`.

## Architecture

**Dependency wiring.** `RetrovikaApp` builds one `AppContainer` holding the repositories and managers. It uses no DI framework. Composables reach it with `LocalContext.current.container` (an extension on `Context`). ViewModels are created with `viewModel { XViewModel(context.container) }`.

**Systems catalog.** `core/systems/Systems.kt` is the single source of truth for consoles. Each `GameSystem` declares:
- file extensions
- an ordered core list (the first entry is the default)
- per-core option `defaults` and `presets`
- BIOS files with MD5 hashes
- orientation
- a `PadLayout` from `emulation/input/PadLayout.kt`
- `libretroDbName`, used for thumbnail URLs

- `keepArchives` for systems whose core runs the `.zip` itself (arcade, DOS), so downloads are not extracted
- `folderOnlyExtensions` for extensions too generic to identify the console on their own (PICO-8 `.png`)
- Citra only presses the 3DS touchscreen with `citra_touch_touchscreen=enabled` (off in the core); its default "mouse" mode moves the cursor with the pointer but presses only with a mouse button, which LibretroDroid never sends. `Systems.kt` sets both
- `portDevice` for cores that ignore input until the frontend calls `retro_set_controller_port_device` (Flycast, Dolphin, Opera, PC-FX, PUAE, VICE, Caprice32, fMSX). It is set on every port before the first `retro_run`. Don't add it to every core: on atari800 a plain JOYPAD replaces its 5200 controller
- BIOS entries without a single MD5 can declare a `format` (`BiosFormat.PS2`): `BiosFormats` checks the content with the core's own rules, Ajustes shows `INVALID` for a right name with wrong content, and import accepts a valid file under any name
- `saveStates = false` for cores whose serialize/unserialize races their own emulation thread (Play! never pauses its VM): no autosave/autoload, slots, sharing or netplay. A racy autosave loaded at startup froze the game later
- `GameSystem.lightweight` (8/16-bit consoles and handhelds): no first-launch core benchmark on MID+ devices. `CoreInfo.needsBios` (SwanStation, LRPS2, ARMSX2): the core only takes part in the benchmark when one of the system's BIOS files is present
- `CoreInfo.autoMax` caps the quality level Auto picks and skips the speed test, for heavy 3D cores whose game start says nothing about gameplay (Dolphin, Citra, YabaSanshiro; see `docs/device-tuning.md`)
- BIOS entries can share a `group`: the group is satisfied when any one file in it is present (3DO, Neo Geo CD)

To add a console, you mostly just add an entry here, plus folder aliases in `RomNaming` and, for cartridge systems with a No-Intro DAT, an entry in `DatCatalog`. `SystemsTest` checks the catalog for consistency. The Gradle `fetchCores` task finds core IDs by regex-matching `CoreInfo("<id>"` in this file, so keep that literal form.

**Cores.** `CoreManager.corePath()` first looks for a core bundled in the APK (`nativeLibraryDir/lib<id>_libretro_android.so`). If there isn't one, it uses the downloaded `filesDir/cores/<id>_libretro_android.so`. Missing cores are downloaded from `buildbot.libretro.com/nightly/android/latest/<abi>/` and marked read-only, which Android 14+ requires for dlopen. They must stay on internal storage. Experimental cores (`CoreInfo.experimental`; LRPS2 gets arm64 crash fixes almost daily) are updated: after a game's first frame `CoreManager.stageUpdate` checks the buildbot (HEAD, ETag kept in `cores/<id>.version`; at most once a day, unmetered networks only) and downloads a newer build to `cores/<id>.next`, and `applyStagedUpdate` swaps it in at the start of the next launch (toast `core_updated`), never under a running core. `buildId` identifies the installed build. Some cores need `systemAssets` from `buildbot.libretro.com/assets/system/` (PPSSPP, Dolphin's `dolphin-emu/Sys`, LRPS2's `pcsx2/resources`, blueMSX's `Machines`/`Databases`). They are extracted into `system/`, and a `.asset-<name>` marker is written only after extraction completes. `CoreManager.needsInstall()` checks both the `.so` and the markers, and installs are serialized per core.

**Core options at launch.** Options are merged in this order (`CoreOptionLayers.merge`): `core.defaults`, then `core.presets[preset]`, then `core.deviceOptions` (options that depend on the device, not on the quality level: a function of `DeviceProfile`, see `docs/device-tuning.md`), then the user's manual overrides stored in DataStore under `core_options_<coreId>`, then the overrides for this game only (`game_opts_<gameId>_<coreId>`, the "This game only" switch of the Core tab; forgotten with the game), then `core.fixed`, which the user can't change and the pause menu hides (the PlayStation memory cards: PCSX ReARMed and SwanStation keep card 1 in the `.srm` and card 2 as a shared file in `saves/psx/`, LRPS2 keeps both shared in `system/pcsx2/memcards/`, and ARMSX2 does the same by default, with no option to change; Play! creates its own under `saves/ps2/Play Data Files/vfs/`). A value the core does not list for that key is replaced by the core's default when the core declares its options, so keys and values in `Systems.kt` must match the core's own list (check with the core's `SET_VARIABLES`). Before creating the view, `GameActivity` points `$EXTERNAL_STORAGE` at `saves/<system>/`, because Play! builds its data folder from it.

**Library.** List queries in `GameDao` select `LIST_COLUMNS` (everything but `description`, read only by `observe(id)`); never write back a `Game` that came from a list. `LibraryRepository.rescan()` merges two sources:
- the internal `roms/<systemId>/` tree (plain file paths, `GameSource.IMPORTED`/`DOWNLOADED`)
- user folders linked through SAF (`content://` URIs, `GameSource.LOCAL`), scanned directly with `DocumentsContract` for speed. With all-files access (Android 11+, or ≤ 9 with read permission) an `externalstorage` tree is listed with `java.io` instead (`StorageAccess.realDir`), building the provider's own doc ids (`primary:dir/file`) so URIs stay identical; the tree root is listed both ways first and any difference falls back to SAF. `Android/data|obb|sandbox` are skipped like the provider does. A scan only builds a `Game` (regexes, cover URL) for URIs not yet in the DB

`RomNaming` decides the system: a folder alias (`ps1`, `megadrive`, …) wins over the file extension, and an extension only identifies a system on its own if it is unique (`Systems.byUniqueExtension`). Scans read every `.cue`/`.gdi`/`.m3u`/`.ccd` first, and only the files those sheets reference are hidden as auxiliary. When a sheet can't be read, `isAuxiliaryFile` falls back to a name heuristic. Removing a SAF game adds its URI to `hiddenGames` in settings, so the rescan doesn't bring it back; Ajustes can unhide them.

**Launching games.** Path-based games pass `gameFilePath` to LibretroDroid. A SAF game on local storage also gets a real path when the user granted all-files access (`StorageAccess.realFile`). Cores marked `needsRealPath` (Play!, LRPS2, bsnes, Mesen, ParaLLEl N64, Panda3DS, SameDuck) open the game with their own I/O instead of the libretro VFS; without that permission they show a screen asking for it, because the virtual path does not exist for them. Otherwise SAF games go through `GameFiles.virtualFiles()`, which opens file descriptors for the main file plus any `.cue`/`.gdi`/`.m3u` references under the fake directory `/retrovika_vfs/`. LibretroDroid's VFS matches those paths by exact string, so references keep their relative subfolder (`disc1/x.cue`) as written in the sheet.

**GameActivity lifecycle (important).** LibretroDroid is a native singleton, which has several consequences:
- `GameActivity` is `singleTask` with its own `taskAffinity`. `onNewIntent` with a different game ID saves and then calls `recreate()`.
- `GLRetroView` observes a private `LifecycleRegistry` (`emulationOwner`), not the Activity's lifecycle. Pausing means moving that registry to `STARTED`. This is how the pause menu freezes emulation.
- In `onPause`, SRAM and the autosave state are written synchronously *before* the registry is moved down (skipped when no frame ran since the last autosave: `lastAutoFrames`). Exiting through the menu captures the state synchronously but compresses and writes it on `app.scope` (`SaveStates.writeAsync`); every `SaveStates` read awaits the pending write of that file, so a quick relaunch never sees a half-written autosave.
- Until the first frame (and the autoload, read early in `prepare`) the GL view stays composed under the `loading` overlay; Back during loading shows "Cancelling…" and exits once `GLRetroView.isLoading` turns false. The menu is shown at once (`menuPending`) while the state is captured with the audio muted; the registry only moves to `STARTED` (`menuOpen`) after the capture, and Save/Translate/netplay wait for `frozenState`.
- Never serialize, unserialize or reset the core off the emulation (GL) thread. GPU cores (N64, Dreamcast, GameCube) make GL calls there and crash or write garbage without the context. The GL thread is stopped while paused, so the state is captured before stopping (on menu open and in `onPause`) into `frozenState`. The menu saves and autosaves from that copy. Load and reset close the menu first, then run on the emulation thread, waiting from `Dispatchers.Default` rather than the main thread. SRAM is a plain memory copy and can be read from any thread.
- `GLRetroView` holds Android focus during play; once the menu is open (`menuOpen`) `menuFocus` makes it non-focusable so D-pad/keyboard keys reach the Compose menu, and `close()` gives focus back. Gameplay input doesn't depend on focus (`dispatchKeyEvent` forwards it).
- The manifest `configChanges` stops rotation from recreating the Activity.
- The screen stays on (`FLAG_KEEP_SCREEN_ON`, `keepScreenOnWhileActive`) only while something runs: the game, loading, a benchmark, a netplay match, a QR code on screen or the remote-play server. With the pause menu open, or on the error screen, it times out like any app. `GLRetroView` sets `keepScreenOn` on itself, so `GameActivity` turns that off on every view it creates.
- `GameScreen` keeps the `AndroidView` at the same composition position in both orientations, so the GL surface is never re-parented.

**Undo in the pause menu.** Loading a slot or restarting from the menu keeps the `frozenState` from before it (`undoState`, one level, this session only); the States tab then shows "Undo". Restart also asks for confirmation.

**Saves.** SRAM is stored as `saves/<system>/<rawName>.srm`, the same naming RetroArch uses. States are `states/<system>/<gameId>/slot<N>.state` plus `.png` thumbnails. Every state on disk goes through `core/storage/RZip` (RetroArch's rzip format: zlib in independent 128 KB chunks, compressed and decompressed in parallel at level 1; core states shrink 25-200x, and writing a few MB is faster than writing the raw state, so the synchronous autosave in `onPause` got shorter); raw states from older versions are still read as they are, and a background thread at low priority compacts them once (marker `states/.rzip-v1`), keeping their dates and never replacing a file that changed meanwhile. `SaveStates.backup` keeps only the two newest `.state.bak` per slot. The same housekeeping thread (in `AppContainer`, 20 s after start) deletes expired `cacheDir/gameinfo` and `cacheDir/explore` files and shared packages older than a day; "Limpar cache" in Ajustes clears those folders too. Slot 0 is the autosave, and its thumbnails come from `PixelCopy`. SRAM is also written every 30 s while the game runs and it changed, so a core crash doesn't lose the in-game saves (on PS1 that is memory card 1).

**Virtual gamepad.** `VirtualGamepad` gives every control its own `pointerInput`. The face buttons share a `FaceGroup`: a finger that went down on one button can slide onto a neighbor or stop in the gap between two (both pressed); drifting into empty space keeps what was pressed. Pressed states are read in `drawBehind`, not in composition, and the opacity is a `graphicsLayer` with `CompositingStrategy.ModulateAlpha` (no full-screen offscreen layer). This is what makes multi-touch work, and it lets touches outside the controls reach the game view (needed for the DS touchscreen). `PadMetrics` holds nominal dp sizes and computes an auto-scale that fits the portrait or landscape area. If you add a `FaceArrangement` or change control sizes, update `PadMetrics` too. Key codes follow the libretro RetroPad convention (A = right, B = bottom, X = top, Y = left). The D-pad and the N64 C-buttons send motion events, not key events.

**Catalog and downloads.** Read `docs/catalog.md` before changing `core/catalog`, the Explore tab, the game page, `core/gameinfo` or the in-app browser. It covers the `CatalogSource` implementations and how duplicates merge, the RomsFun Cloudflare and IP-pinned links, the download queue and the game-info sources (Backloggd, Wikidata, HowLongToBeat).

**Visual identity.** The theme is "synthwave sunset" (`ui/theme/Theme.kt`). `Palette.Neon` (pink) is the primary accent, `Cyan` the secondary, and `SunsetGradient`/`SunsetHorizontal` (pink → orange → yellow) are used for primary buttons, the active tab and the brand. Fonts are bundled in `res/font` (OFL): Space Grotesk (`DisplayFamily`, the Material typography), JetBrains Mono (`MonoFamily`, labels) and Press Start 2P (`PixelFamily`, only for `Wordmark` and `Kicker`). Build screens from the shared pieces in `ui/components/Components.kt`: `ScreenHeader`, `HeaderIconButton` (every round header button, with optional badge/busy state), `SectionHeader`, `GradientButton`/`GhostButton`, `SelectChip`/`AccentChip`/`ChipStrip` (instead of M3 `FilterChip`; chips are `selectable`, min 36dp tall), `FilterLabel`, `Modifier.bleed()` (chip strips inside a padded grid run to the screen edge), `Modifier.shimmer()`/`GameCardSkeleton` (loading placeholders instead of a lone spinner), `IconTile`, `SearchField`, `SurfaceCard`, `DownloadProgressBar`, `EmptyState(icon = …)`, `Modifier.ambientGlow()` and `Modifier.focusRing(source, shape)` (neon outline for D-pad/TV focus; `pressScale` also grows focused items). Clickable cards and buttons use `indication = null`, so anything new that is clickable that way needs `focusRing`, or controllers can't see the selection. Colors come from `Palette` (`OnAccent` for content on the sunset gradient, `HeroGradient` for highlight cards), not literals. Long-pressing a `GameCard` opens `GameQuickMenu` (play, favorite, page, remove via the shared `RemoveGameDialog`). From 600 dp wide the tabs move to a side `TabRail` (always shown, marking the tab that owns the current stack) and the game page splits into two panes. The tab bar floats over the content, so tab screens add `LocalBottomInset.current` to their bottom `contentPadding`. The logo is an "R" whose counter is a play button, in front of a striped sun: `ic_launcher_background` (scene) + `ic_launcher_foreground` (monogram) + `ic_launcher_monochrome`; `ic_logo` (layer-list) is used by the splash, and `BrandMark` draws it in Compose.

**Languages.** No user-visible string is hardcoded in Kotlin. Strings live in resources: `res/values/` is English (the fallback for any other system language) and `res/values-pt/` is Portuguese. Every key must exist in both. `strings.xml` holds the shared keys (`common_*`, `tab_*`, the `games_count`/`consoles_count` plurals, `region_*`), and each area has its own `strings_<area>.xml`. Enums and catalog data carry `@StringRes` ids, not text (`Preset.label`, `ShaderOption.label`, `CoreInfo.description`, `BiosFile.description`). Use `stringResource`/`pluralStringResource` in composables. Outside the UI, use `context.localized().getString(...)`, because the Application context isn't recreated when the language changes below Android 13. Regions are stored in the DB in Portuguese at scan time (`RomNaming.region`, `regionOf`) and translated only at display time with `regionLabel()`. The language picker in Ajustes goes through `core/settings/Languages.kt`:
- On Android 13+ it uses the system per-app language (`LocaleManager`, `res/xml/locales_config.xml`).
- Below that, it stores the choice in SharedPreferences and `Languages.wrap` is applied in `attachBaseContext` of the Application, `MainActivity` and `GameActivity`.

**Navigation.** `ui/navigation/RetrovikaNavHost.kt` uses string routes. The tabs are `home`, `library`, `explore`, `downloads` and `settings`; pushed screens are `system/{id}`, `game/{id}`, `catalog/{key}`, `browser`, `settings/cores` and `settings/bios`. Tapping the open tab again emits its route on `LocalTabReselect`, and each tab screen calls `ScrollToTopOnReselect(route, state)` with its list state. `AppSettings.reduceMotion` turns the screen transitions off. The NavHost also owns the SAF folder-picker launcher and runs a rescan on startup.

**Repeated versions.** `core/library/Versions` groups a console's files by clean title (the DAT name when identified; disc numbers stay in the key, so disc 2 is never a "duplicate" of disc 1) and scores each one: the app language's region or a translation into it (`[T+Por]` beats the English original for Portuguese users), DAT verification, `[!]` and newer revisions win; `[b]`, hacks, trainers and betas lose. `system/{id}/versions` shows the groups, bulk-verifies with `DatRepository.identifyAll` and removes the others.

**Cheats.** `CheatRepository` lists `libretro-database/cht/<libretroDbName>/` through the GitHub API (`contents/cht` for the folder SHA, then `git/trees/<sha>`, because the contents API stops at 1000 files) and caches the list for a week. Per-game choices live in `cheats/<system>/<id>.json`. `CheatSession` backs the pause-menu tab; the activity re-applies the whole enabled list (`resetCheat` + `setCheat`) on the emulation thread when the menu closes and after the first frame. The same tab has a memory search (`RamStudio`, `RamSearchPanel`, pure logic in `core/cheats/RamSearch`): a snapshot of the core's `RETRO_MEMORY_SYSTEM_RAM` (`LibretroDroid.readSystemRam`, up to 64 MB; `systemRamSize` is 0 when the core doesn't expose it), filters (changed, up, down, equal to, changed by N with wrap-around at the value width), and "Lock", which saves a `ram:<addr>:<value>:<width>[:be]` code (`RamCheat`) in the game's cheat list. These codes never reach `setCheat`: `applyCheats` splits them off and `LibretroDroid.setRamFreezes` makes the native step write them into the RAM after every `retro_run` (under `coreLock`, so it also works in fast-forward). Cleared when netplay starts. Some cores only allocate the RAM after loading (N64, GameCube, PSP report 0 bytes or a null pointer at load), so `systemRamSize` is asked when the search opens and the native log says "System RAM exposed by the core" twice (at load, after 30 frames). The N64 cores keep RDRAM in host-endian 4-byte words: the `sw` flag (`RamCheat.wordSwap`, on by default for `n64`) reads logical byte N at N xor 3. The RAM goes into two reused arrays (`LibretroDroid.readSystemRamInto`, `RamSearch.takeRetired`); `RamStudio` checks `RamSearch.bytesNeeded` against the free heap before the snapshot and turns an `OutOfMemoryError` into a warning (a 32 MB PSP RAM peaks at about 160 MB of Java heap). Not exposed: yabasanshiro.

**Config files per game.** Read `docs/core-config-files.md` before touching what a core reads from disk. Dolphin reads `saves/<system>/User/GameSettings/<discId>.ini`: the Core tab has a "Game config file" editor (text kept in DataStore `game_ini_<gameId>`, written by `GameActivity.syncGameIni` before the core opens, marked `; Retrovika game profile`, never over a file the user placed). PPSSPP's `ppsspp.ini` and per-game ini are looked up at `/` and are unreachable; RetroAchievements through the cores did not start in the two cores checked.

**Controller per game.** Besides `pad_console_<system>`, a game can have its own `pad_game_<id>` profile (menu › Controls › "This game only"). Profile writes go through an ordered, unbounded queue because each one may target a different key.

**Sharing states.** A `.rvstate` is a zip (`manifest.json`, `state.bin`, `thumb.png`, see `StatePackage`). It goes out through the share sheet (FileProvider `${applicationId}.files`) or over the LAN: `LanTransfer.Server` serves it on a raw TCP socket with a token (no HTTP: cleartext is blocked and there is no certificate for a LAN IP) while a `retrovika://state` QR code is on screen. `MainActivity` turns VIEW/SEND intents and deep links into `AppContainer.incoming`; `ReceiveHost` matches the game (`StatePackage.match`: DAT name, raw name, file name, then title with the same region) and launches `GameActivity` with `state_file`/`core_id`. Such a session (and a netplay guest) is a `guestSession`: neither SRAM nor autosave is written.

**Live translation.** `LiveTranslator` reads the frame and translates it in three steps. Capture: `GameActivity` asks LibretroDroid for the core's own frame (`requestFrameSnapshot`/`takeFrameSnapshot`: native resolution, no shader or filtering, plus the game area inside the view); GPU cores and rotated games fall back to the `PixelCopy` of the view. The frame is enlarged by an integer factor with nearest-neighbor (`TranslationText.upscaleFor`), since pixel fonts are too small for the recognizers. OCR: `MeikiOcr` (MeikiOCR, D-FINE detector plus a recognizer that detects each character, trained on Japanese game text; decoding in `MeikiDecode`) runs on ONNX Runtime when the optional `OcrPack` is installed (Ajustes › Tradução da tela, ~58 MB: three models from Hugging Face pinned by revision and SHA-256, and `libonnxruntime.so` pulled out of the Maven Central `.aar` with `RemoteZip`, HTTP Range on that one entry). The APK only carries the small JNI bridge (`packaging.jniLibs.excludes`); `MeikiOcr` `System.load`s the downloaded runtime first, so keep `onnxruntime` in `libs.versions.toml`, `OcrPack.RUNTIME_AAR` and its hashes on the same version. ML Kit's Japanese recognizer (unbundled, `ocr_ja` manifest dependency; it also reads Latin text) reads Latin text and Japanese without the pack. `TranslationText.groupLines` joins lines into blocks (short lines stay alone: menu options). Translation: with a Gemini key (`AppSettings.geminiKey`, kept in the `secrets` SharedPreferences, which are outside the cloud backup, model `gemini-flash-latest` by default), `GeminiTranslator` sends the PNG plus the OCR lines and gets JSON blocks (`GeminiText`: OCR line ids or `box_2d` 0–1000, corrected original, translation), with the game title and the session's recent lines as context; if it fails, the regular path runs and the overlay says why. The regular path sends each block to `translate.googleapis.com` and uses ML Kit on-device translation only offline. Japanese is always translated; English only for Portuguese users. The activity captures the frame and the state (like opening the menu), pauses, and `TranslationOverlay` draws each translation over its original box. **Text from memory.** The "game memory" the app sees is the core's `RETRO_MEMORY_SYSTEM_RAM` followed by the other writable regions the core describes in `SET_MEMORY_MAPS` that do not overlap it (`Environment::environment_handle_set_memory_maps`, `LibretroDroid::memoryView`; the GBA adds its 256 KB EWRAM, the GB its HRAM…); addresses are positions in that sequence, `readMemoryRange` reads a window and `queueMemoryWrite` writes once after the next frame. A game can have text hooks (`core/textmem`: `TextHook` = address, length, encoding ASCII/UTF-16/Shift-JIS/linear table, `wordSwap` for the N64; stored per game in DataStore `game_hooks_<gameId>`). The memory search panel creates them: the player types a phrase they see on screen, `TextSearch.find` looks for it in the RAM (exact in each encoding, plus a relative search for non-ASCII tables like Pokémon's) and "Use" saves the place. When the player translates, `GameActivity.memoryTranslation` reads only each hook's window (`TextDecoder.window`), decodes its segments and `LiveTranslator.translateTexts` translates them (no OCR): with a Gemini key, one text-only request (`GeminiText.textRequest`: game context, session history and each text's character limit) and Google/ML Kit for whatever it leaves out or if it fails (after a failure the text path skips Gemini for 60 s, since the auto loop asks every 500 ms); without a key, Google/ML Kit as before. Translations are kept per game and language in `translations/<system>/<gameId>.<lang>.json` (`TranslationMemory`, LRU of 5000, flushed in `onPause`/`onDestroy`, deleted with the game): a stored text is shown or written back without the network; the overlay shows cards (`TranslationUi.Ready.fromMemory`) because the text has no position on screen. No hooks, an unreadable RAM or nothing decoded falls back to the OCR path. A game with hooks always gets the Translate button, and there the HUD button does something else: `TextPatcher` rewrites the translation **into the game's memory** (`GameActivity.translateInGame`), so the game's own text engine shows it. `TextSegment.capacity` (the text plus the zero bytes that follow it, up to the next non-zero byte) bounds every write; a longer translation is shortened (`TextEncoder`: transliteration, word cut with "..." — or with nothing when a table has no byte for "." —, line wrapping to the original width); the patcher passes each text's character limit to the translator (capacity minus terminator, halved for UTF-16 and full-width). A Shift-JIS original with no half-width letter or digit gets the translation in full-width characters (`fullWidth`, 2 bytes each), since many Japanese fonts have no half-width glyphs; `alreadyTranslated` sees NFKC-normalised text. The "Translate dialogs in the game" switch (`game_auto_translate_<gameId>`) repeats it every 500 ms for new text, waiting for the text to be stable across two reads and reusing translations already made. Text-mode screens (C64, MSX, DOS) use `TextHook.gridWidth`: each row is a segment, and a row only counts when almost all of its bytes decode. `LinearTable` may have only upper or lower letters (the other is folded), learns punctuation, completes the space and `asciiLow` (C64 screen codes) in `TextSearch.completeTable`. Hooks can be copied/pasted as JSON. **Automatic discovery** (no search, no OCR): while the auto loop runs, `TextWatcher` scans the RAM every 1.5 s (4 s above 8 MB; after the first full scan only the ranges around changed 32-byte blocks, extended to the nearest `00 00`, are rescanned, and last-seen hashes are kept even when the text vanishes, so a dialog box that closes and reopens with another line still counts) for text-like runs (ASCII sentences, UTF-16 Latin or kana, Shift-JIS starting at kana) and keeps a hash of each; a run whose content changes at a fixed address between two scans is a buffer the game rewrites (the dialog box), and becomes a hook named `Auto: …` (`GameActivity.discoverStep`, saved like any hook; at most 48; static data never changes, so it never qualifies; the first scan only records). The auto switch defaults to on for Japanese games (region/`(Japan`) or with `translateEverywhere` (`translatesByDefault`; the per-game choice, true or false, wins) and is shown in every game (the pause menu "Game" tab), so the player can turn it on or off anywhere. The same scan also hashes the RAM in 32-byte blocks; regions that changed between two scans go to `TableDetector`, which finds an English linear table (letters in sequence from any byte) with no sample text: for each possible first byte it reads the window as letters and counts common English words, then learns the space (the byte most often between two letters), the capitals block (most words with a capital initial, conventional offsets first), the comma and (with two occurrences) the period, and the terminator. A hit becomes a `TABLE` hook. When the layout is shifted ASCII (lower − upper = 32 and the space where ASCII puts it), digits and punctuation are filled from the same shift. Lower/upper candidates whose 26-byte block can't reach the minimum are skipped through a byte histogram. `tools/make-dialog-test-rom.py` with `TABLE_SHIFT=96` builds the ROM with shifted bytes to test it. Not covered: tables that are not linear (letters not in sequence), compressed or DTE text, text printed straight from ROM, and languages other than English for the table path. `tools/make-dialog-test-rom.py` builds a Game Boy ROM that redraws a WRAM dialog every frame (A changes the message), used to test all this.

**Core benchmark and device tuning.** Read `docs/device-tuning.md` before changing `core/tuning`, `CoreBenchmark`, `SpeedWatch` or `DeviceProfile`. It covers the first-launch benchmark, the quality levels, the per-game results, frameskip and thermal handling, the crash and Vulkan safety nets, and the PS2 cores.

**Frame pacing and the libretro engine.** `libretrodroid/README.md` lists every change to LibretroDroid; the ones that matter for performance: `FPSSync` uses vsync when the screen runs 1–4× the content rate (on 120 Hz a 60 fps game runs one frame every 2 vsyncs and `Video::representFrame` redraws the last one in between), otherwise it sleeps *before* running the frame and outside `coreLock`. `GLRetroView` asks the display for the content rate (`Surface.setFrameRate`, `ONLY_IF_SEAMLESS`, cleared while paused), follows refresh changes with a `DisplayListener` (`setScreenRefreshRate`) and keeps an ADPF hint session for the GL thread on API 31+ (`step()` returns the work time without the sleep). The frontend implements the audio-buffer status callback, so the cores' "auto" frameskip works (inactive while muted, fast-forwarding or in netplay: the benchmark never skips), plus `SET_MINIMUM_AUDIO_LATENCY`, `GET_AUDIO_VIDEO_ENABLE`, `GET_FASTFORWARDING`/`GET_THROTTLE_STATE`, `SET_SYSTEM_AV_INFO` timing and `GET_PERF_INTERFACE`. `GLRetroView.fastForwardHints` is set only by the player's fast-forward (`applyFastForward`): it tells cores they are fast-forwarding and lets software cores skip drawing intermediate frames; the benchmark must never set it. `videoFrameCount()` (new frames from the core) next to `runCount()` (retro_run calls) feeds `SpeedWatch` and the optional performance HUD (`AppSettings.showPerformance`). `FrameRendered` is emitted once per view, and key/motion events go straight to native (`inputLock`), not through `queueEvent`.

**Local netplay.** `libretrodroid/.../netplay.cpp` is input-delay lockstep: before each `retro_run` of frame F each side sends its input for F + delay and runs F only once the other side's input for F arrived; otherwise the frame is skipped (the GL thread never blocks on the network). `handleSetInputState` answers ports 0/1 from the synchronized pads while a match is on. The Kotlin side (`core/netplay`, `NetplayController`) pairs through a `retrovika://netplay` QR code and uses two TCP sockets: control (text lines `INFO`/`JOIN`/`OK`/`STATE`/`RESYNC`/`BYE`) and input, whose fd is detached and handed to native. The host serializes the state and starts netplay in one emulation-thread step (`serializeAndStartNetplay`); the guest does the mirror (`unserializeAndStartNetplay`). Fast-forward, state loading, reset, core options and cheats are blocked during a match.

**App updates.** `core/update/AppUpdater` reads `api.github.com/repos/SamwellOt/Retrovika/releases/latest` once per process (`checkOnStartup`, off with `AppSettings.checkUpdates`) or from Ajustes › Atualizações, compares the tag with `versionName` (`Versions.newer`), downloads the attached `.apk` into `cacheDir/updates/` and checks that its package and signing certificate match the installed app before handing it to `PackageInstaller`; `UpdateInstallReceiver` opens the system confirmation (`STATUS_PENDING_USER_ACTION`) and reports failures. `UpdateCard` shows it on Home ("Depois" stores `dismissedUpdate`) and in Ajustes. The release notes come from `.github/release-notes/<tag>.md`, so keep them readable as plain text. Since 0.6.7 a release carries the universal `Retrovika-x.y.z.apk` (created first, and first by name: older updaters take the first `.apk`) plus `Retrovika-x.y.z.<abi>.apk`; `parseRelease` picks the device's ABI and falls back to the universal one, never another ABI.

**Baseline Profile.** `app/src/main/baseline-prof.txt` covers the app and the LibretroDroid bridge with wildcard rules; AGP expands them before R8 (`expandReleaseArtProfileWildcards`) and R8 rewrites them. No Macrobenchmark module.

**Remote play** (`remote/`, pause menu tab "Tela e controles"). Read `docs/remote-play.md` before changing `RemotePlay`, `RemoteServer`, the video path or `assets/remote/`. It covers the HTTP/WebSocket server, the two bilingual pages, the video encoder modes and the audio path.

**Diagnostics.** Ajustes › "Enviar relatório de erros" (`core/diagnostics/ErrorReport`) shares device/GLES info, `ApplicationExitInfo` and the app's own recent logcat, which still holds the native backtrace and core messages of a crashed game on the next launch. Ask users for it when a core crashes on a device you can't reach.

**Ideas for later.** `docs/ideas.md` lists differentiating features not implemented yet (AI companion, rewind, RetroAchievements…), each with the pieces it builds on.

## Constraints

- Library versions are pinned in `gradle/libs.versions.toml` (AGP 8.13, Kotlin 2.2, compileSdk 36). AGP 9.x is not in use.
- Release signing reads `keystore.properties` (template: `keystore.properties.example`) or `RETROVIKA_*` env vars, and falls back to the debug key with a warning locally. The `release.yml` workflow fails without the `RETROVIKA_KEYSTORE_BASE64` secret: every release must be signed with the same project key (from 0.3.4 on), or the in-app updater can't install it over the previous one. Never commit the keystore or its properties.
- With targetSdk 36, Android 16 delivers Back only through `OnBackPressedDispatcher`, not as `KEYCODE_BACK`. `GameActivity` handles both paths.
