# Core benchmark and device tuning

Detailed notes for the core benchmark and the per-device quality levels. CLAUDE.md has the overview; read this before changing these areas.

**Core benchmark.** The first time a console runs without a user-chosen core (`AppSettings.autoBenchmark`), `GameActivity.runBenchmark` runs the stable cores with the game, muted, at `frameSpeed` 8, each with its own `LifecycleRegistry`. Speed = emulated frames (`LibretroDroid.getRunCount`) / time / content fps. `CoreBenchmark.choose` keeps the first core in catalog order with ≥130% speed, else the fastest, so the test walks the cores in catalog order (`CoreBenchmark.next`) and stops at the first one with ≥130%: the later ones are left out of the results and shown as "not tested" (`untested`), never as failed. Each measurement stops after 1.5 s of foreground time once the speed is unambiguous (`CoreBenchmark.isDecided`: ≥ 2 × `UP_PROBE` or ≤ 0.5 × `HEADROOM`), 4 s at most. Cores with `needsBios` only run when a system BIOS is present (`BiosManager.canRun`), and `lightweight` systems skip the test on MID+ devices (`skipForLightweight`; nothing is stored, the default core is used). Core downloads during the test show progress in `BenchmarkView`. `measure` turns every auto-frameskip option off (`Tuning.withoutAutoFrameskip`, list `AUTO_FRAMESKIP`, checked against the core-options JSONs by `AutoFrameskipTest`): PPSSPP's auto frameskip follows the wall clock and would inflate an uncapped run; fixed frameskip levels of a preset stay, since they apply in play too. The audio-buffer-driven ones are also neutralized natively (the buffer is reported inactive while muted). Results live in `bench_<system>`; `effectiveCoreFor` = user choice ?: benchmark. Results carry the device (`SettingsRepository.BENCH_DEVICE`) and are ignored on another phone. Progress is written to `filesDir/benchmark/benchmark_<system>.json` (`GameActivity.BENCH_DIR`, outside the backup) before each core; nothing is stored when no core produced a speed, so a core that crashes the app counts as failed on the next launch.

**Device tuning.** `core/tuning` adapts the quality level of each core to the device. `DeviceProfile.detect` reads the SoC, RAM, the highest CPU frequency from sysfs (some vendors block it: then only the GPU counts) and `GL_RENDERER` from a throwaway EGL pbuffer (cached in the `device_profile` prefs); `AppContainer.deviceProfile` is lazy. `DeviceTier` (ENTRY/MID/HIGH/TOP) is the worst of the GPU and CPU scores, capped by RAM. The levels are the `Preset` entries a core declares in `presets` (`Tuning.ladder`); a core with fewer than two takes no part, so a new tuned core needs `presets` in `Systems.kt` (keys and values checked against the core's `SET_VARIABLES`). `Tuning.effective` picks the level, in this order: the game's own result (`tune_game_<id>`), the user's console choice (`preset_<system>`; absent = "Auto"), the result measured for that console and core (`tune_<system>_<core>`), and a guess by tier (`Tuning.estimate`). A stored `TuneResult` carries `DeviceProfile.signature` and the core id and is ignored when either differs (a restored backup on another phone). Measuring (`GameActivity.runTuning`, before the core is installed and started) runs on the first launch of a core with no user choice and `autoBenchmark` on, or on demand with the `retune` extra (game page, "Optimize this game", stored per game): it reuses `measure` of the core benchmark (same headroom, frame speed, `EmulationUi.Benchmarking` with `BenchKind`) and `Tuning.search` starts at the guess (when the core benchmark just measured the same core with exactly the same options map, `CoreBenchmark.reusable` hands that speed to the search instead of measuring it again), steps down until a level has `CoreBenchmark.HEADROOM`, and climbs only while the speed leaves `UP_PROBE` of room. Progress goes to `filesDir/benchmark/benchmark_<system>_<core>_quality.json` (`benchmark_game_<id>.json` per game) before each level, so a level that kills the app counts as failed next time; leaving the screen mid-test does not. Skipping stores the guess with `skipped` so the test does not come back. While a game runs, `SpeedWatch` (one sample per second, only with the game in front, no menu, no fast-forward, no netplay and no connected remote screen, whose encoder shares the CPU) fires when most of a 10 s window, after 15 s of grace, ran under 85% speed: the game then gets the level below stored in `tune_game_<id>` (`slowdown`) for the next launch, with a toast; when the level is the user's own console choice it only toasts and stores nothing. It counts slow time, not the average: a loading screen is not a slow game. With an auto-frameskip option on (`Tuning.autoFrameskipOn`), the run speed stays near 100% while the player sees fewer frames, so each sample also carries `videoFrameCount` (new frames delivered by the core): a sample is slow too when its skip share is more than 0.20 above the session baseline (20th percentile of the last 300 samples). The baseline absorbs fixed frameskip and 30 fps games that dupe frames; samples under 20 runs or with >90% skip (static screens) are ignored. Known limit: a long 30 fps scene after minutes of full-rate play looks slow once. Auto frameskip itself comes from `deviceOptions` on ENTRY/MID only (genesis_plus_gx, picodrive, mgba, gpsp, snes9x2010): those cores ask for ~100 ms more audio latency while it is on. **Thermal** (`core/tuning/Thermal.kt`, API 29+): `GameActivity` listens to `PowerManager` thermal status; at SEVERE it toasts once per session (`thermal_hot`), and when `SpeedWatch` fires while the status is MODERATE+ now or within the last 15 s, nothing is stored (the slowness is throttling, not the game) and `thermal_slowdown` is shown instead. `DeviceProfile.perfCores` counts the CPU cores within 80% of the fastest one's frequency (`fastCores` falls back to half of them when sysfs is blocked). **PS2:** `src/test/resources/core-options/<core>.json` holds the option keys and values each core declares, read from the arm64 binaries of the buildbot (core options v2 tables found through the `R_AARCH64_RELATIVE` relocations; the Play! ones are v1 `"Desc; a|b"` strings), and `CoreOptionsTest` checks every `defaults`/`presets`/`fixed` (and the `deviceOptions` of every non-Vulkan core, for all four tiers) of those cores against them, so a wrong key or value fails there and not silently on the phone (refresh the file when changing `Systems.kt`). Since 2026-10-05 the set also covers genesis_plus_gx, picodrive, mgba, snes9x2010, gpsp, handy, desmume, dolphin, citra and yabasanshiro, built from each core's `libretro_core_options.h` on its default branch rather than from the binary (`README.txt` says which). Dolphin (`dolphin_efb_scale`, `dolphin_shader_compilation_mode`), Citra (`citra_resolution_factor`) and YabaSanshiro (`yabasanshiro_resolution_mode`) have three-level ladders, but **`CoreInfo.autoMax`** caps what Auto picks for them and turns the speed test off (`Tuning.measurable`): the test measures the first seconds of a game (logos, loading), which say nothing about 3D scenes, so in 0.6.5 it climbed to Dolphin 3x with ubershaders and Citra 4x and those games ran slowly. With a cap, Auto is the tier estimate up to the cap, a stored measured result is ignored, a per-game result is clamped to the cap (`SpeedWatch`/`SessionGuard` can still step a game down) and the game page hides "Optimize this game"; only the user's own choice goes above it. Caps: Dolphin BALANCED, which is the core default that ran until 0.6.4 (1x, synchronous shaders; PERFORMANCE adds `dolphin_vi_skip`, QUALITY is 2x); Citra PERFORMANCE (1x, as before); YabaSanshiro BALANCED (2x, the old default). Never use Dolphin's ubershader modes (`1`, `2`; `CoreOptionsTest` rejects them): under LibretroDroid Dolphin gets no shared context for its shader worker threads (logcat: "Failed to initialize shader compiler worker thread"), so every mode compiles shaders inline and ubershaders only add their GPU cost. Flycast's `reicast_auto_skip_frame` is inert while threaded rendering is off (as it is here), so PERFORMANCE keeps the fixed `reicast_frame_skipping`. Play! (GLES 3, the only PS2 core that fits LibretroDroid) tunes `play_res_multi` (1x/2x/4x). LRPS2 links no GL library: its GPU renderers are desktop OpenGL (it demands `ARB_shading_language_420pack`, so it cannot run on GLES) and Vulkan through the frontend's libretro context, so it declares `vulkan = true` and `deviceOptions` picks `pcsx2_renderer = Vulkan` when `DeviceProfile.vulkan` (the device declares Vulkan 1.1+) and `Software (SW)` otherwise (then `pcsx2_upscale_multiplier` is capped at 1x and `pcsx2_sw_renderer_threads` follows the spare fast cores: those beyond the EE, VU1/MTVU and GS threads, at most 1 on an ENTRY device). The Vulkan path: `GLRetroViewData.allowVulkan` (`core.vulkan` and `GameActivity.vulkanAllowed`) lets `libretrodroid` accept `RETRO_HW_CONTEXT_VULKAN`; `VulkanHealth` (prefs `vulkan_health`) counts every launch with Vulkan as an attempt that only the first rendered frame confirms, two in a row without it (a driver that kills the app can't be caught) switch Vulkan off for that core on that device, and `ERROR_GL_NOT_COMPATIBLE` while starting (or later, when the native Vulkan context is lost: `VulkanContext::isLost` makes `step` raise it) relaunches at once with the `no_vulkan` extra (a toast says the core draws on the CPU). Crashes after the first frame are caught by `SessionGuard`: once the first frame arrives, `GameActivity` writes `filesDir/benchmark/session.json` (game, core, level, Vulkan and its key, pid) and deletes it when the game leaves the foreground or the core has been unloaded on exit. A file left by a dead process is read at the next launch with `ApplicationExitInfo` (native crash, ANR, or no reason below Android 11 = crash; low memory = memory; anything else is ignored): the game gets the level below (`TuneResult.crashed`, unless the level is the user's choice) and, for a Vulkan crash, `VulkanHealth.sessionCrashed` counts 2 per crash and `sessionEnded` takes 1 off per clean session of 5 min or more, switching Vulkan off at 4 (two crashes in a row, or crashes in more than half of the sessions; toast `vulkan_off_crashes`). The `VulkanHealth` key is the device signature plus `CoreManager.buildId` (`AppContainer.vulkanKey`), so a new core build tries Vulkan again; the console page shows the switch-off with a "Try again" button (`forget`). `pcsx2` and `ppsspp` have `vulkan = true` (PPSSPP's `deviceOptions` sets `ppsspp_backend` to `vulkan` or `opengl`; its default `auto` follows the preferred renderer, which is GLES). A core with the flag must never ask for Vulkan when `DeviceProfile.vulkan` is false (`CoreOptionsTest` checks it): PPSSPP aborts the process at `dlclose` when it asks for Vulkan and the bridge fails. For that, `AppContainer.deviceProfile` only keeps `vulkan = true` after `LibretroDroid.probeVulkan()` (a native self-test with a throwaway EGL context) passed once per `Build.FINGERPRINT`; `VulkanHealth.bridgeWorks` writes "running" before it and "ok"/"failed" after; a leftover "running" gets one more try (as "retry"), so only a probe that kills the app twice is not repeated. User core overrides that would ask for Vulkan when it isn't allowed for the launch are dropped (`withoutVulkan` in `GameActivity.optionsFor`). The user can turn Vulkan off per core (system page chip, `no_vulkan_<core>` in DataStore). Other Vulkan-capable cores (ParaLLEl N64) need their own test before they get the flag. Ajustes › "Este aparelho" shows the profile and clears every measurement; the console page shows the source of the level ("Auto: Quality, measured…") and the game page lets the user redo or drop the per-game result.
