# Remote play

Detailed notes for the pause-menu remote screen (`remote/`, `assets/remote/`). CLAUDE.md has the overview; read this before changing these areas.

**Remote play** (`remote/`, pause menu tab "Tela e controles"). `RemotePlay` (in `AppContainer`) runs `RemoteServer`, a hand-written HTTP + WebSocket server (no dependency; one thread per connection plus a writer thread and queue each, so a slow device never blocks the encoder), on port 8080 or a free one, bound only to the Wi-Fi/hotspot address from `LanAddress` (never all interfaces: the mobile-data side can have a public IPv6; `LanAddress` also skips `rmnet`/`ccmni`/VPN interfaces, whose 10.x CGNAT addresses look private). The server pings every connection every 10 s and drops one silent for 35 s, and a device reconnecting with the same `id` replaces its old connection (the old tab gets `replaced` and stops reconnecting), so a phone that left the Wi-Fi doesn't keep its player slot. Any exception in a connection thread is caught, since an uncaught one would kill the app. While at least one device is connected it holds a Wi-Fi lock (`WIFI_MODE_FULL_LOW_LATENCY`, `HIGH_PERF` below Android 10; `updateWifiLock`, not while the server just waits): in power-save mode the phone's Wi-Fi only receives on the router's beacons, about 100 ms apart. Two pages from `assets/remote/`, bilingual by `navigator.language`, need no app:
- `pad.html` (the QR code opens `/pad?c=<code>`): a touch controller built from the console's `PadLayout` (`RemotePlay.layoutJson`), one WebSocket per phone. Each gets the lowest free port 1–3 (port 0 is the game phone, ports of physical controllers are skipped) and gets the same one back when it reconnects (`id` in localStorage). Messages are JSON `k` (key) and `m` (motion, the same sources as `PadListener`); on disconnect everything it held is released. Core rumble for that port goes to the phone (`navigator.vibrate`).
- `tv.html` (`http://<ip>:8080`, 6-digit code): the game with sound. It can also ask for players (`join` with a local `p` slot) for the keyboard and Gamepad API controllers on that computer.

Video: after each rendered frame, `Capture` (`libretrodroid/src/main/cpp/capture.cpp`) copies the game area of the window into a texture (`Video::copyForeground`) and, with the `VideoEncoder` input surface current, draws it there (`drawCapture`) on the emulation thread. Don't blit straight from the window with the encoder as draw surface: ANGLE scales that cross-surface read by the wrong surface size. GLES 3 only (`GLRetroView.supportsCapture`). H.264 (Baseline, 1280x720, 6 Mbps) goes out as fragmented MP4 (`Fmp4`) played through Media Source Extensions, which also works on plain `http://`, unlike WebCodecs and AudioWorklet. `VideoTrack` holds each frame until the next arrives and gives it the exact duration: MSE treats a jump bigger than twice the previous duration as a discontinuity and drops everything until the next keyframe. `Avc.lowDelaySps` rewrites the SPS in the init segment with a VUI `bitstream_restriction` and `max_num_reorder_frames = 0`: Android encoders rarely send it, and without it Chrome's hardware decoder (and Windows' in Firefox) holds frames until the level's DPB is full, up to 9 at 720p. The page keeps near the newest frame, checked after every append (seek when > 0.2 s behind, 1.5x when > 100 ms, 1.25x when > 60 ms, 1.1x when > 35 ms). Binary packets start with a type byte: 1 init, 2 video, 4 video keyframe, 3 audio. When the page has to drop queued frames it restarts at a keyframe (or asks for one with `key`), and on a player error it sends `restart` to get the init segment again. `VideoEncoder` has four modes, from lowest latency to most compatible (hardware realtime + low latency, low latency only, plain, software): when the codec dies after starting (Xiaomi SM6375 with `KEY_PRIORITY` realtime), fails to start, or no frame arrives within 12 s, `RemotePlay` stops the capture and tries the next one; the mode that delivered video is saved per app version (`remote_play` prefs). Only after the last mode fails do the menu and the page say so. Audio: `handleAudioCallback` also copies samples into a ring buffer (`Capture::writeAudio`, before the "audio enabled" check, so the phone can be muted while the TV plays); `RemotePlay` sends 20 ms PCM chunks that the page schedules with Web Audio. Each packet carries its sample rate and `pumpAudio` rereads `audioSampleRate` every loop, so a core that changes its rate mid-game (`SET_SYSTEM_AV_INFO`, which recreates the native Audio) needs no encoder work. The encoder runs only while a screen is connected. The server survives game changes (`recreate()` re-attaches the new `GLRetroView`) and stops when the game is exited (`isFinishing`). The code is compared first, so a right code always passes; only wrong ones are counted, per IP (20 in a minute) and across all IPs (60), and past that each wrong one waits 5 s and gets 429, on the WebSocket and on `/qr.svg` alike. The request head must arrive within 5 s, and each IP may hold at most `MAX_PER_ADDRESS` connections. Test it with headless Chrome over CDP against the redroid address; its display runs at 15 Hz, so it only emulates about 30 frames a second, with or without streaming.
