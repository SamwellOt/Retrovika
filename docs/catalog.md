# Catalog, downloads and game info

Detailed notes for the catalog, the download manager, the in-app browser and the game page. CLAUDE.md has the overview; read this before changing these areas.

**Catalog and downloads.** `CatalogSource` implementations are registered in `CatalogRepository`: `CdRomanceSource`, `RomsFunSource` (only when built with a `WebFetcher`, so JVM tests create the repository without it), `HomebrewHubSource` and `InternetArchiveSource`. The list order is also the preference order: `CatalogRepository.mergeDuplicates` joins every page of the same game (same system and normalized title, `dedupKey`; a trailing "DVD5"/"DVD9" is ignored) into one card, whether the pages come from different sources or repeat inside one (RomsFun has several pages for some games). The card keeps the position where the game first appeared, the entry of the earliest source in the list is the main one and the rest go to `CatalogEntry.alternates`. `ExploreViewModel` applies it again as each page or source arrives, and in single-source views too. `downloadKey` is the `dedupKey`, so it doesn't change when a card is merged. In the Explore source filter, CDRomance and RomsFun are one chip, "Roms" (`ROMS_GROUP` in `ExploreViewModel`, `searchAll(only = …)`), and cards tag them as "Roms" too; the real site name only shows when downloading (variant picker, game page's download panel). On the game page, `CatalogRepository.variants` lists the files of every merged page in parallel, each `RomVariant.origin` pointing at its page (a failing source doesn't hide the others), `directLink` uses that origin, and `details` falls back to the next page when the main one fails. In `HomebrewHubSource`, search uses `q`, because `title` is case-sensitive, and `developer` can be a string or an array. A source can override `directLink(entry, variant)`: it runs inside the download job (and again on retry), for links that are signed and expire. The Explore tab has special **genre filters** (`core/catalog/Genre.kt`): no source has a real genre taxonomy, so `search(..., genre)` is best effort per source. Homebrew Hub sends the genre to its API as a `tags=` filter (`hubTag`: server-side, so pages are not empty; filtering locally made sparse genres chain request after request), CDRomance appends `Genre.searchTerm` to the WordPress `?s=` search, run inside the console's section (`/<section>/?s=`) when a console is chosen so the site filters it, the Internet Archive adds a `subject:(…)` clause, and RomsFun uses the site's own genre taxonomy (`GENRE_TERMS`). The UI says results are approximate. `CatalogRepository.search` caches recent pages for a few minutes, `CatalogSnapshots` keeps the last first page of each filter without a search term on disk (`cacheDir/explore`, shown at once while the search refreshes it), and `searchAll(onPartial = …)` shows each source as soon as it answers. When a filter yields few games per page, `ExploreViewModel` fetches the next pages in parallel (`PARALLEL_PAGES`) until the screen is filled. `DownloadManager` runs downloads in the app scope through a queue, kept alive in the background by `DownloadService` (a `dataSync` foreground service started while `activeCount` > 0, which stops itself when the queue empties): at most `AppSettings.maxDownloads` run at once (the rest stay `QUEUED` and start in the order they were requested), and each task keeps its work so `retry(id)` can redo it. Tasks report bytes, total and a smoothed speed from `Http.download(onBytes = …)`; UI that only needs the counter observes `activeCount`, not `tasks`, so it doesn't recompose on every progress tick. It extracts `.zip`/`.7z` through `RomExtractor` (except for arcade; disc games with `.cue`/`.gdi`/`.m3u` get every track extracted), and registers the result through `LibraryRepository.addDownloaded`. `LibraryRepository.importFiles` uses the same extractor. `Archives` detects the format by magic bytes and uses commons-compress `ZipFile`/`SevenZFile`, so Deflate64/ZIP64 work. `.7z` goes first through `SevenZipNative` (`app/src/main/cpp`, the public-domain LZMA SDK in `cpp/lzma/`), which decodes Copy/LZMA/LZMA2 blocks in chunks with the dictionary in native memory: "ultra" archives need 256 MB+ of dictionary, more than the Java heap of many phones even with `largeHeap`. Other methods (BCJ, BCJ2, PPMd) fall back to commons-compress before anything is written. Password-protected archives (encrypted `.zip` via zip4j, AES `.7z` via commons-compress, which skips the native path) are opened with the passwords that sites publish (`RomExtractor.KNOWN_PASSWORDS`). `Http.download(parallel = N)` fetches big files (≥ 8 MB) in pieces over N HTTP/1.1 connections when the server answers a `Range: bytes=0-` probe with 206 (hosts that cap speed per connection get several times faster); a piece that gets 503/429 goes back to the queue and that connection quits, only the last one waits. `DownloadManager` uses 4 connections, except for RomsFun (its file hosts ban the IP) and browser downloads (cookies). `Http.client` keeps 24 idle connections (Coil shares it). `Http.download` waits and retries on 503/429 (ROM file hosts answer "server is busy" under load), honoring `Retry-After` (capped at 5 min) for up to 16 minutes in total, and reports each wait through `onWait`; `DownloadTask.retryAt` shows it as a countdown (`busyWaitText`). It also resumes with Range when a connection drops (`If-Range` with the ETag/Last-Modified, also on every parallel piece, so a file swapped on the server restarts instead of mixing). A failed single-connection download keeps its `.part` as an `Http.ResumePoint`, so `retry(id)` continues it; cancel, success and removal drop it. Free space is checked once the size is known, and `ENOSPC` is never retried. Every failure must reach the screen as a readable reason: throw `LocalizedException`, and show it with `Throwable.userMessage(context)`, which also turns network and disk errors into plain text.

**RomsFun.** Everything on romsfun.com is behind a Cloudflare challenge (OkHttp gets 403), so `RomsFunSource` has its own `WebFetcher` (`minGapMs = 400`: about 30 quick fetches give 429 plus a new challenge; `WebFetcher.request` then reopens the site and retries once). Search is `/browse-all-roms/` with `q`, `consoles[]` (numeric ids, all supported consoles when none is chosen, so pages aren't full of PS3/Xbox games) and `genres[]`; the site's `/?s=` ignores genre. Download: the game page links `/download/<slug>-<id>`, whose table lists the files. For 3DS, `.cia`, "eShop" and "(Theme)" rows are dropped because the core can't run CIA; a table with only those raises `romsfun_only_cia`. Each file page `/download/<slug>-<id>/<n>` gets its real link from `POST admin-ajax.php` `action=k_get_download`, with the file page as `referrer`. The `href` already in the page HTML is a decoy that the server rejects. The signed link (`sto*.romsforever.co`, `sto.romsfast.com`) only works from the IP that requested it: `directLink` reads the WebView's IP from `/cdn-cgi/trace` and pins OkHttp to IPv4 or IPv6 (`Http.clientFor`); a mismatch returns 403 "Sorry, your request is invalid". When a file host shows its own challenge, `WebFetcher.solve()` opens it in the WebView, and OkHttp sends that `cf_clearance` with `WebFetcher.userAgent`. A page counts as past the challenge when its document is loaded, has a host and doesn't carry the challenge title (`WebFetcher.pageCleared`); the cleared root of `sto2` is plain text with no `<title>`, so never require one. When the hidden WebView doesn't pass (Cloudflare asking for the "Verify you are human" tap, or past the 20 s), `WebFetcher.askUser` hands the page to `ChallengePrompt` (`AppContainer.challenges`) and `ChallengeHost` (in the NavHost) shows it in a dialog that closes by itself once it clears; with the app in the background it fails at once with `web_check_blocked`. The fetcher must not block images: the challenge never finishes without them. File hosts: `sto.romsfast.com` (no challenge, but IP-pinned), `sto2.romsforever.co` (challenge; a Google Drive index that answers big files with 503 `{"error":"The server is busy…"}` and `Retry-After: 300` even when the 1-byte probe passes) and `statics.romsfun.com` (challenge for OkHttp from desktop, passes from Android). Too many requests from one IP make the file hosts answer 503 for minutes (up to an hour), so test sparingly. Some `og:image` URLs are `http://` and are upgraded to https.

**Catalog game page.** Tapping an Explore card opens `catalog/{key}` (`ui/screens/explore/CatalogGameScreen.kt`); the route carries only the `downloadKey`, and `CatalogRepository.open/opened` keeps the entry in memory while the page exists. `CatalogGameViewModel` loads its parts in parallel, each as a `Part` (loading, ready, failed), so a failure never hides the rest:
- `CatalogSource.details(entry)`: the source's own sheet (`SourceDetails`). RomsFun reads the header (rating, downloads, genre), the info table, `.page-content` and `#romGallery`. CDRomance reads the `table.rom-info` rows, the users' `aggregateRating`, `#custom-description` and the `#lightgallery` screenshots (the game page is cached, since the download reads it again). Homebrew Hub reads `/api/entry/<slug>.json`; the Internet Archive reads `/metadata/<id>`.
- `variants(entry)`: the files; sizes the listing lacks come from a `HEAD` (`Http.contentLength`).
- Backloggd (`core/gameinfo/BackloggdClient`): no public API, so it uses the site's `autocomplete.json` and parses the game page (JSON-LD `AggregateRating`, `#ratings-bars-height` histogram) plus `/reviews/preview/<slug>/`. Among same-name games it keeps the earliest one released on the console (`Platforms` maps system IDs to IGDB platform slugs/names). Its BunnyCDN sometimes answers with a JavaScript check (403, "Establishing a secure connection"), depending on the IP; the cookie it sets only works on the browser's own connection, so from then on `WebFetcher` makes the requests from inside an invisible WebView with `fetch()` (results come back through a `@JavascriptInterface`).
- Wikidata/Wikipedia (`WikiClient`): found by the Backloggd slug (it is the IGDB slug, Wikidata `P5794`) or by title; gives developers, publishers, series, director, composer, modes, age ratings, critic scores (`P444`/`P447`), links (HowLongToBeat, MobyGames, Metacritic, IGDB) and the article summary in the app language.
- HowLongToBeat (`HowLongToBeatClient`): the time to beat comes from here, not from Backloggd. The game ID is Wikidata's `P2816` (`WikiInfo.hltbId`), so it loads after Wikipedia; `/game/<id>` works with plain OkHttp (browser User-Agent) and carries everything in `__NEXT_DATA__`: main story, main + extras, completionist, all styles and speedrun (`comp_*` in seconds, `comp_*_count` players). The site's search needs a rotating token, so games without the Wikidata ID just don't show the section.
`CatalogGameViewModel.loadGameInfo` runs them side by side: Wikipedia by title starts with Backloggd and shows as soon as it arrives, HowLongToBeat starts when the Wikidata entity gives its ID (`onHltbId`, before labels and summary), and the Backloggd slug only replaces the article when it points to another item; Backloggd fetches the likely candidate's reviews together with the pages. `GameInfoRepository` caches all three in memory and on disk (`cacheDir/gameinfo`, 3 days; "not found" 12 h). `BackloggdClient` remembers across launches (`net_hints` prefs) that the CDN challenged this network, goes straight to the WebView, and `ExploreViewModel` warms that WebView up (`WebFetcher.warm`). `WebFetcher` is ready as soon as the real document is interactive, without waiting for every image. An idle `WebFetcher` page closes after 3 min, or after 20 s while `MainActivity` is stopped (a game is open or the user left: the site's scripts would keep running; `AppContainer.setUiInBackground`); the RomsFun one keeps the normal delay while downloads are queued. `GameTitles.clean` turns ROM names into database titles. `GameInfoNetworkTest` checks all of this against the real sites in the `catalog-speed` workflow.

**In-app browser.** `ui/screens/browser/BrowserScreen.kt` is a WebView for sites that can't be a `CatalogSource` (Cloudflare challenges, token flows). The user browses normally; `DownloadListener` captures the file, `RomNaming.guessSystem` pre-selects the console from the extension or page URL/title, and `DownloadManager.enqueueBrowser` downloads it with the WebView's cookies, User-Agent and Referer. `Http` keeps a User-Agent set on the request instead of overriding it.
